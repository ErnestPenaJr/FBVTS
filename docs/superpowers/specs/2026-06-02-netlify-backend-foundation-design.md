# Netlify Backend Foundation — Design Spec

**Date:** 2026-06-02
**Status:** Approved (pending final spec review)
**Sub-project:** #1 of 3 (Backend foundation → Role management + impersonation → Messaging)

## Goal

Convert FBVTS from a frontend-only vertical slice (all state in `localStorage`,
simulated auth) into a real multi-user application with a shared, durable
Postgres backend on Netlify and real email/password authentication.

This is sub-project #1. It is the prerequisite for two follow-on specs that are
**explicitly out of scope here**:

- **#2 Role management + impersonation** — super-admin/manager promote users to
  elevated roles; a super-admin-only "view as role" / impersonation tool.
- **#3 Messaging** — in-app messaging subsystem.

Neither can exist without the identity model and backend built here, so #1 ships
first.

## Decisions (from brainstorming)

- **Goal:** true shared backend + durable storage (multi-user, everyone sees the
  same live data).
- **Auth:** email + password (self-contained; no third-party provider).
- **Liveness:** data is fresh on load / after an action (refetch model). No
  polling, no real-time push in v1.
- **Roles:** everyone registers as `volunteer`; elevation happens via the
  super-admin/manager tooling in sub-project #2. The free role-switcher is
  removed from normal flow (returns super-admin-only as the impersonation tool in
  #2).
- **Initial DB state:** seed demo *content* (volunteer-role catalog, campuses,
  service times, events) but **no demo user/signup accounts**. Super-admin
  bootstrapped from an env-var password.
- **Client architecture:** Approach 1 — `AppContext` stays the single source of
  truth; hydrate from the API on load, write-through on each action. The
  `useApp()` interface barely changes.
- **Backend stack:** Netlify Functions + Neon serverless driver + **Drizzle ORM**
  + SQL migrations checked into the repo.
- **Super-admin email correction:** `epena@fallbrookchurch.org` (was `.com`) —
  already corrected in `src/types.ts` and the super-admin docs.

## Architecture

```
React SPA (Vite — routing/components unchanged)
        │  fetch('/api/...') with httpOnly session cookie
        ▼
Netlify Functions  (netlify/functions/* , exposed as /api/* via redirect)
        │  Neon serverless driver + Drizzle
        ▼
Netlify DB (Neon Postgres)
```

**Pieces:**

- `netlify/functions/` — backend endpoints. Each validates the session cookie,
  re-derives the caller's identity + role **server-side**, runs the query via
  Drizzle, returns JSON.
- `netlify/functions/_lib/` — shared helpers: `requireAuth(req)` (parse + verify
  cookie, load user), `requireManager` / `requireEventManager` /
  `requireSuperAdmin` wrappers, JSON/error helpers, JWT sign/verify, bcrypt.
- `netlify/db/` — Drizzle schema (`schema.ts`), Neon connection
  (`client.ts`), and `migrations/` (SQL files generated by `drizzle-kit`).
- `netlify.toml` — redirect `/api/*` → functions, alongside the existing SPA
  fallback.

**Server-side authority:** the client role becomes advisory (UI gating only).
Every function independently derives identity + role from the verified session
and rejects unauthorized writes. `SUPER_ADMIN_EMAIL` power is derived server-side
from the authenticated email, mirroring today's client derivation.

**Dev workflow shift:** `npm run dev` switches from plain `vite` to
`netlify dev`, which runs Vite + functions together and injects the Neon
connection string locally.

## Data model (Postgres schema)

`Position` moves from an embedded array on `ServiceTime`/`AppEvent` into its own
table. `Settings` (font scale) folds onto the `users` row. IDs stay text in the
existing `uid(prefix)` format so seed data ports cleanly.

```
users
  id            text PK
  name          text not null
  email         text not null unique (lower-cased / citext)
  phone         text
  photo_url     text
  bio           text
  role          text not null default 'volunteer'   -- volunteer|event_manager|manager
  password_hash text not null      -- bcrypt; never returned to client
  font_scale    text not null default 'normal'
  created_at    timestamptz default now()

volunteer_roles
  id text PK, name text not null, description text,
  default_needed int, category text

campuses
  id text PK, name text not null, address text not null

service_times
  id text PK, campus_id FK→campuses (on delete cascade),
  day_of_week text not null, time text not null

events
  id text PK, name text not null,
  campus_id FK→campuses (on delete cascade),
  manager_id FK→users, date date not null, time text not null

positions
  id          text PK            -- per-slot; signups.position_id references this
  role_id     FK→volunteer_roles (ON DELETE RESTRICT)
  needed      int not null
  parent_kind text not null      -- 'service' | 'event'
  parent_id   text not null      -- service_time.id or event.id
  index (parent_kind, parent_id)

signups
  id text PK,
  user_id     FK→users (on delete cascade),
  kind        text not null,     -- 'service' | 'event'
  ref_id      text not null,     -- service_time.id or event.id
  position_id FK→positions (on delete cascade),
  unique (user_id, kind, ref_id, position_id)
```

**Constraints replicate today's hand-written logic:**

- Cascades replace the manual cleanup in `AppContext` (deleting a campus removes
  its services/events/signups).
- `positions.role_id ON DELETE RESTRICT` enforces the "can't delete a volunteer
  role in use" rule at the DB level (function returns a clean 409).
- The `signups` UNIQUE constraint replaces the client-side `exists` check and is
  race-proof.
- Capacity ("X of Y filled") stays computed via `COUNT` of signups per position —
  never stored, exactly as `positionFilled` does today.

## Authentication & sessions

**Endpoints:**

- `POST /api/auth/register` — `{ name, email, password }`. Validate, ensure email
  free, bcrypt-hash, insert **always as `volunteer`**, set session cookie, return
  safe user (no hash).
- `POST /api/auth/login` — `{ email, password }`. Look up by email,
  `bcrypt.compare`, set cookie. Generic "invalid email or password" on failure
  (no user enumeration).
- `POST /api/auth/logout` — clear cookie.
- `GET /api/auth/me` — current user from cookie, or 401.

**Session mechanics:**

- Signed **JWT** (HS256, `JWT_SECRET` env var) carrying `{ userId }` only — never
  the role. Role is always read fresh from the DB, so promotions/demotions take
  effect immediately and a stale token cannot carry elevated privilege.
- Stored in an **`httpOnly`, `Secure`, `SameSite=Lax` cookie**, ~30-day expiry;
  logout clears it.
- `requireAuth(req)` verifies the cookie + loads the user; `requireManager` /
  `requireEventManager` / `requireSuperAdmin` build on it.

**Super-admin bootstrap:** the seed step upserts `epena@fallbrookchurch.org` with
`role = 'manager'` and a bcrypt hash from `SUPER_ADMIN_INITIAL_PASSWORD`. If the
env var is unset, bootstrap is skipped (never ship a default password).
Super-admin *power* remains derived from the email server-side.

**Login screen change:** the one-click user-picker is replaced by a real login
form + register link. The role-switcher is removed from normal flow.

## API surface

All endpoints validate the session via `requireAuth`; structural writes go
through `requireManager` / `requireEventManager`, mirroring today's
`isManager` / `isEventManager` gates. JSON in/out. Error shape `{ error: string }`
with status codes: 400 validation, 401 unauthenticated, 403 wrong role, 409
conflict. Write endpoints return the created/updated row so the client updates
context without a full re-hydrate.

**Bootstrap:**

- `GET /api/state` — single hydrate call. Returns everything for the current
  user: `users` (safe fields only), `volunteerRoles`, `campuses`,
  `serviceTimes` (with positions), `events` (with positions), `signups`, and the
  current user. Called once on app load. (Reads are one bootstrap call; writes
  are granular.)

**Volunteer roles** (manager-only writes):

- `POST /api/roles`, `PATCH /api/roles/:id`, `DELETE /api/roles/:id`
  (DB RESTRICT → 409 if in use).

**Campuses / service times / events:**

- `POST|PATCH|DELETE /api/campuses/:id` — manager-only.
- `POST|PATCH|DELETE /api/service-times/:id` — manager-only.
- `POST|PATCH|DELETE /api/events/:id` — event-manager+. `manager_id` set
  server-side from the session, never trusted from the client.

**Signups** (any authenticated user, for themselves):

- `POST /api/signups` — `{ kind, refId, positionId }`; `user_id` is the session
  user. UNIQUE constraint → double-signup is a clean 409/no-op.
- `DELETE /api/signups/:id` — only if owned by the caller (or caller is manager).

**Profile / settings:**

- `PATCH /api/profile` — name, phone, bio, photoUrl for the session user.
- `PATCH /api/settings` — font scale.

## Client side (`AppContext`, Approach 1)

The `useApp()` interface stays almost identical. What changes is boot + the
internals of actions.

**Boot sequence:**

- `AppProvider` starts in `loading`. On mount it calls `GET /api/state`.
- Statuses: `loading` → full-screen spinner; `error` → "couldn't reach server,
  retry" screen; `ready` → hydrate `PersistedState` from the response, render.
- A 401 from `/api/state` / `/api/auth/me` → no session → render the
  login/register flow (replaces today's `RequireAuth` localStorage check).

**Actions become async:**

- Each action `POST/PATCH/DELETE`s to its endpoint, then merges the returned row
  into context state. Signatures go from `() => void` to `() => Promise<void>` so
  call-sites can `await` and show pending/disabled button states.
- On failure, the action throws/returns an error; the component surfaces it via
  the existing `Toast`.
- **No optimistic updates in v1** — apply server truth on response (no rollback
  logic). Fits "fresh on load" + low contention.

**Removed:**

- The `localStorage` write-through `useEffect` and `loadState()` — replaced by
  server hydration. (May keep persisting **only** `fontScale` locally to avoid a
  font flash before `/api/state` returns.)
- `register`/`login` become API calls; `switchRole` removed from normal flow
  (returns super-admin-only in #2).

**Unchanged:** derived values (`isManager`, `campusName`, `positionFilled`,
`roleUsage`, …) — they compute off hydrated state.

**Accepted trade-off:** one coarse "loading the app" state instead of per-section
spinners; a one-time refactor of action call-sites for `async` + pending UI.

## Seeding, migration & local dev

- **Migrations:** `drizzle-kit` generates SQL into `netlify/db/migrations/`,
  checked in. `npm run db:migrate` applies them.
- **Seed** (`npm run db:seed`): ports `src/data/mockData.ts` content — role
  catalog, campuses, service times (+ positions), events — into Postgres. Does
  **not** seed demo users/signups. Idempotent (upsert by id).
- **Super-admin bootstrap:** part of seed; upsert `epena@fallbrookchurch.org` as
  `manager` from `SUPER_ADMIN_INITIAL_PASSWORD`; skip if unset.
- **Local dev:** `netlify dev` runs Vite + functions and injects the Neon
  dev-branch connection string. `.env` (gitignored) holds `DATABASE_URL`,
  `JWT_SECRET`, `SUPER_ADMIN_INITIAL_PASSWORD`; same vars in Netlify env for prod.
- **Existing localStorage data is not migrated** — it's demo data; the seeded
  catalog replaces it. The old `fbvts-state-v2` key is abandoned.

## Errors, security & verification

**Error handling:** uniform `{ error }` JSON + status codes; client actions catch
and surface via `Toast`; boot failure shows the retry screen.

**Security:**

- bcrypt hashes, never returned to the client.
- JWT in `httpOnly` / `Secure` / `SameSite=Lax` cookie.
- Role re-read from DB every request; all writes role-gated server-side.
- SQL injection avoided via Drizzle parameterization.
- `JWT_SECRET` / DB creds only in env, never in the client bundle.

**Verification** (no test runner; type-check is the gate per CLAUDE.md):

- `npm run lint` (`tsc -b`) stays clean — Drizzle inferred types cover the
  schema/query layer.
- Manual flows documented in the plan:
  - register → login → logout.
  - A volunteer signs up; a second browser/user sees the updated count on reload.
  - Manager-gated writes rejected for a volunteer (verified by calling the API
    directly with a volunteer session).
  - Super-admin bootstrap login works.
- Optional lightweight function-level checks, but the convention is type-check +
  manual QA.
